# 員工效能 × 流失原因分析 —— 設計稿（待核准，2026-09-05）

兩個模組共用同一份正規化資料（leads / conversations / messages / funnel_events / appointments / visits / deals / evidence）。
目的不是「誰好誰壞」，而是：誰在產生結果、為什麼、強在哪、客戶在哪裡流失、結果裡哪一部分真的是他做的、管理層該教什麼或改什麼。
每一個重要結論都要有：指標 ＋ 樣本數 ＋ 對照 ＋ 對話／成交證據。

## 1. 歸因模型（attribution）

每一位客戶（lead）可以掛多個「角色」，一個人一個角色一次；規則全部決定性、可回溯到訊息。

| 角色 | 判定規則 | 證據 |
|---|---|---|
| 主要業務 PRIMARY | 結案時 `leads.staff_id`（成交帳本 `deals.staff_id` 優先） | 帳本列 |
| 支援 SUPPORTING | 非主要業務、在結案前於同一對話發過 ≥1 則實質訊息（非交接宣告、非貼圖／圖片） | 那幾則訊息 |
| 主管介入 MANAGER | admin／operator 在結案前發過 ≥1 則訊息，或帳本標記主管參與 | 那幾則訊息 |
| 交接 HANDOFF（交出／接手） | `assignment_log` 有紀錄；沒有帳本時，對話中發言業務由 A 變 B 且之後 A 不再發言 → 新事件 `STAFF_HANDOFF`（信心 STRONGLY_SUGGESTED） | 交接訊息＋前後發言者 |
| 回流貢獻 REACTIVATION | `RE_ENGAGED` 前 7 天內有該業務的 `FOLLOW_UP`；客戶自己回來的不算 | 跟進訊息＋回流訊息 |

**直接 vs 影響**
- 直接成交／直接毛利：只算主要業務。
- 影響成交／影響毛利：此人以任一角色出現的成交案，每案只算一次、不拆分金額（例：直接 7 台／影響 11 台；直接毛利 42 萬／影響 61 萬）。
- 畫面同時顯示兩個數字，影響數字一律標「關聯」，不寫成「他帶來的」。
- 不做金額拆分（70/30 之類）——那是權重決策，見 §7。

## 2. 員工指標定義與門檻

| 群組 | 指標 | 定義 | 最低樣本（否則「資料不足」） |
|---|---|---|---|
| 活動 | 處理客戶數 | 期間內為主要業務的 lead 數 | — |
| | 進行中對話 | 未結案且 30 天內有訊息 | — |
| | 回覆中位數 | 客戶每則訊息→業務下一則回覆的間隔中位數 | ≥10 則 |
| | 跟進一致性 | 客戶沉默 48h 後、7 天內有業務跟進的比例 | ≥5 次沉默 |
| | 停滯客戶 | 進行中但 14 天無業務訊息 | — |
| | 交接／回流 | 交出、接手、回流貢獻次數 | — |
| 漏斗 | 報價→預約 | 報價過的客戶中之後預約成立的比例 | ≥10 |
| | 預約→到店 | 預約成立中之後到店的比例 | ≥8 |
| | 到店→成交 | 到店中之後成交的比例 | ≥5 |
| | 整體成交率 | 成交 ÷ 已結案（成交＋流失）；進行中不算分母 | ≥10 已結案 |
| | 客戶流失率 | 流失 ÷ 已結案 | 同上 |
| 商業 | 成交台數／營收／毛利 | 帳本，結案日在期間內 | — |
| | 每台毛利／平均售價／平均成交天數 | 帳本 | ≥3 台 |
| | 影響營收／影響毛利 | §1 | — |
| 協作 | 支援案數、成功交接、跨組貢獻、主管介入次數、幫到別人的成交 | §1 角色計數 | — |

排名規則：
- 每個排名維度各自排，**沒有黑箱總分**；每列都印樣本（例：成交率 42%，21/50）。
- 未達門檻的人不排名、顯示「資料不足」，不用 0 填。
- 小樣本高比例不會排在大樣本之前：排序鍵＝Wilson 下界（95%），畫面仍顯示原始比例＋樣本。
- 「需要關注」只在該人已結案 ≥10 且某指標低於團隊平均一個明確幅度（比例低 10 點以上、或回覆中位數是團隊 2 倍以上）時出現；文字用「觀察到的模式」，不寫「造成」。
- 脈絡欄：客戶量、車價帶（該人客戶的中位車價）、在職期間（資料裡第一則訊息）、缺資料註記；比較表可依車價帶分層看。

## 3. 流失原因引擎（lost-deal reason）

對每一位「未成交結案」與「疑似流失」的客戶，讀整段對話，輸出：

`loss_analyses(lead_id, primary_reason, secondary_reason, confidence, stage, evidence[message_id…], staff_id, supporting_ids, vehicle_id, appointment_status, visit_status, outcome, first_at, last_customer_at, last_staff_at, method, computed_at)`

類別（先用規格的 17 類，真資料進來再修）：
價格抗拒｜貸款問題｜車款不符｜車況疑慮｜舊車折抵談不攏｜時機未到｜家人決定｜別家買了｜無車可賣｜業務回覆太慢｜跟進不足｜預約爽約｜客戶停止回覆｜隨便看看／低意圖｜議價破局｜其他｜不明／證據不足

判定順序（規則優先，AI 只補「不明」）：
1. 帳本 `lost_reason` 有明確類別（價格／貸款／別家買了…）且對話有對應訊號 → CONFIRMED。
2. 對話訊號：`PRICE_OBJECTION`＋之後沒預約／沒議價成功 → 價格抗拒；`FINANCING_QUESTION` 未解決＋沉默 → 貸款問題；`NO_SHOW` 後無重新預約 → 預約爽約；`NEGOTIATION` 後 LOST → 議價破局；詞庫命中（車況／折抵／家人／再想想／別家）→ 對應類別。信心依訊號強弱：明講＝STRONGLY_SUGGESTED，只有一則暗示＝POSSIBLE。
3. 只有沉默、沒有任何訊號 → 主因「客戶停止回覆」，**副因**看流程：最後一則是客戶且業務 48h 內沒回 → 「業務回覆太慢」；沉默後沒有任何跟進 → 「跟進不足」。這兩個是流程面原因，標「流程」，不是客戶原因。
4. 都沒有 → 不明／證據不足；AI 可讀整段對話提出一個假設，但必須引用實際訊息 id，畫面標「假設」，且不進總計。

「哪裡掉」＝LOST 前最後到達的漏斗階段（從事件推，不用 `leads.stage`，因為結案後一律是 closed）。
另一個「替代可能」欄位：規則找到第二強的訊號時填入（例：價格抗拒；替代：可能還在比較其他車）。

## 4. 彙總視圖

- 流失原因 Top N＋對照前期（本期 34 位未成交：價格 12、貸款 7、爽約 5、車款不符 4、別家 3、不明 3）。
- 分項：業務、車款、車型、漏斗階段、價格帶（<60 萬／60–100／100–150／150+）、組別；每格附 n，點進去是那幾位客戶的對話。
- **員工 × 流失原因矩陣**：列＝業務，欄＝原因，格＝該人已結案客戶中此原因的比例＋n，底列團隊平均；比團隊高 10 點以上且 n≥5 才標琥珀。
- 員工檔案裡再加：最常流失的原因、最常流失的階段、流失是客戶面還是流程面（比例）、價格異議後有沒有跟進、貸款問題有沒有給答案、預約→到店、到店→成交。
- 句型固定為「觀察」，例：「王XX 到店→成交很強（92%，n=12），但報價階段流失高於團隊平均（38% vs 24%，n=21）。」不寫「因為他」。

## 5. 團隊效能與協作

- 團隊層：轉換、營收、毛利、客戶量、回覆時間、預約、到店、成交、交接成功率（交接後仍成交的比例）、跨組支援次數。
- 組合：兩人同時出現在同一客戶（任一角色）的案子數、其中成交數、比例；一律標「關聯」，n<5 不顯示比例。
- 貢獻圖：單一客戶的角色鏈 客戶 → 主要業務 → 支援 → 主管介入 → 交接 → 結果 → 營收／毛利，每個節點可點到訊息。

## 6. 問 AI 要支援的問法（意圖擴充）

流失原因（本週為什麼沒買／最大原因／某車款為什麼不轉換／哪些原因在增加／貸款造成的流失）、
員工（誰報價後流失最多／誰最會救回沉默客戶／誰毛利貢獻最高／成交強但跟進弱的是誰／哪些組合最常一起成交／某人預約轉換為什麼低／每個人本週該改什麼）。
每一題都走現有的三段式（規則意圖 → 決定性數字＋客戶＋證據 → AI 只講人話），數字白名單閘門照舊。

## 7. 待 Curry 決定的事

1. **總貢獻分數要不要做**。若做，建議五個維度、公式全部公開，畫面同時列原始指標與加權分：
   商業結果（直接毛利）／影響毛利／漏斗效率（三段轉換相對團隊）／客戶處理（回覆、跟進一致性、停滯）／團隊貢獻（支援、交接、回流）。
   **初步權重提案：30 / 10 / 25 / 20 / 15**——未經同意不會寫進程式。
2. 影響毛利是否要做金額拆分（例：支援者分 30%），還是維持「每案算一次、不拆分」。建議不拆分，因為拆分比例本身就是黑箱。
3. 「需要關注」的門檻：已結案 ≥10 且低於團隊平均 10 點——太嚴或太鬆？
4. 模擬資料要補的劇本：主管介入、同事支援、正式交接（寫進 assignment_log）、車況疑慮、折抵談不攏、家人決定、時機未到、別家買了、無車可賣。補了才能展示這些欄位不是空的。
5. 流失原因類別是否照規格 17 類，或先合併成 10 類（價格、貸款、車、折抵、時機／家人、別家、流程：回覆慢／跟進不足／爽約、停止回覆、低意圖、不明）。

## 8. 實作順序（核准後）

1. 資料：`STAFF_HANDOFF` 事件、`lead_roles` 表（lead_id, user_id, role, evidence）、`loss_analyses` 表；模擬劇本補齊 §7-4。
2. 引擎：`engine/attribution.ts`（角色）、`engine/loss.ts`（原因）、`engine/staff.ts`（指標、門檻、Wilson 排序、需要關注）。
3. 評測：流失原因 precision／recall 對生成器真值（門檻同 D-004），交接／回流角色的命中率。
4. API：`GET /api/staff`（總表＋排名＋矩陣＋組合）、`GET /api/staff/:id`（檔案）、`GET /api/loss?days&by=`、Ask 意圖擴充。
5. 前端：`/staff` 與 `/staff/:id`，照核准的參考畫面。

## 2026-09-05 晚：訊息組 vs 業務、共用座位、估算毛利
- 角色多一種 `chat_handler`（`users.job='chat'` 的人在結案前回過訊息）；訊息組→業務的移交不算交接。
- 訊息面指標（首次回覆、回覆中位數、沉默後跟進、行為特徵、報價後續走、預約轉換）算在「線上回訊息的人」（`behaviors.chat_staff_id`＝發最多文字訊息的員工）；成交面指標算在 `leads.staff_id`（接待群指派的業務）。訊息組的到店→成交、成交率、毛利標「不適用」，不進排名；純業務的訊息面指標同樣不適用。
- `users.seat_shared=1`：個人訊息面指標 `shared=true`（畫面「共用帳號」），只算到團隊。
- 毛利只算 `deals.cost_source<>'none'` 的成交；`gp_is_estimate=1` 標「估算」。`commercial.gp_known / gp_unknown / gp_estimate` 三個數字每頁都帶。
- 對話 `coverage` 不是 full：不算回覆速度與沉默後跟進；流失原因不判回覆太慢／跟進不足（`docs/DATA_FLOW.md` §2）。
